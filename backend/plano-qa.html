01Visão Geral

Identificação do sistema sob teste e dos objetivos de qualidade desta iteração.

SUT — Sistema sob Teste

  • RESOLVE APP — Plataforma de registro eletrônico de solicitações e ocorrências urbanas
  • Conecta cidadãos à administração pública municipal
  • Backend: Node.js/Express · Microserviços · PostgreSQL · Redis
  • Mobile: React Native / Expo · Android
  • Repositório: BatistaIsabella/RESOLVE-APP

Objetivos desta suíte

  • Verificar sistematicamente os contratos de API expostos pelos microserviços
  • Validar regras de negócio, autenticação e controle de acesso por perfil
  • Mapear cenários mobile E2E para futura automação com Appium/Detox
  • Identificar falhas, limitações e comportamentos inesperados no SUT
  • Fornecer base reproduzível de feedback contínuo de qualidade

Serviços em Escopo

  • auth-service · porta 3001 · Registro e login JWT
  • demand-service · porta 3002 · CRUD de denúncias
  • App mobile Android · React Native/Expo

Fora de Escopo (esta iteração)

  • metrics-service (porta 3003)
  • api-gateway (porta 8080)
  • Frontend web (Next.js)
  • iOS / dispositivos Apple
  • Testes de carga e performance

04Ambiente e Pré-requisitos

Configuração necessária para execução local dos testes automatizados.

Infraestrutura

  • Node.js ≥ 18.x
  • PostgreSQL rodando (schemas: public, demand)
  • Redis rodando em localhost:6379
  • Migrations aplicadas em ambos os serviços

Variáveis de Ambiente

  • DATABASE_URL_AUTH — conexão auth-service
  • DATABASE_URL_DEMAND — conexão demand-service
  • JWT_SECRET — deve ser idêntico nos dois serviços
  • REDIS_URL — demand-service

Execução — auth-service

  • cd backend/auth-service
  • npm install
  • npx prisma migrate deploy
  • npx vitest run
  • npx vitest run --reporter=verbose

Execução — demand-service

  • cd backend/demand-service
  • npm install
  • npx prisma migrate deploy
  • npx vitest run
  • npx vitest run src/tests/TS05_operacoes_gestor.test.ts
05Análise de Riscos

Riscos identificados e estratégias de mitigação para o ciclo de testes.

IDRiscoProbabilidadeImpactoMitigação
R01 JWT_SECRET diferente entre serviços invalida tokens nos testes Alta Alta Configurar JWT_SECRET idêntico via .env ou docker-compose
R02 Redis indisponível causa falha em testes do demand-service Média Média Subir Redis via Docker antes de rodar os testes; timeout de 3s já implementado
R03 Dados de teste deixados no banco após falha intermediária Média Baixa Todos os testes possuem afterAll com cleanup; usar banco dedicado para testes
R04 Filtros avançados (categoria/status/região) não implementados no backend Alta Média Cenários marcados como it.skip() até implementação; documentado no TS04
R05 Testes E2E mobile dependem de emulador/dispositivo configurado Média Alta Documentar pré-requisitos do emulador Android; usar Device Farm no CI/CD

10Bugs e Achados

Comportamentos inesperados identificados durante a análise e automação do SUT.

🔴
BUG-01 — Rotas incorretas no TS04 (testes existentes). O arquivo TS04_filtros_avancados.test.ts usa /demandas/demands, /demandas/demands/feed e /demandas/gestor/demands. As rotas corretas são /demandas/my-demands, /demandas/feed e /demandas/gestor. Os testes de paginação estão testando endpoints 404 silenciosamente.
🟡
BUG-02 — JWT_SECRET padrão inconsistente. O authMiddleware.ts do demand-service usa fallback 'change-me', enquanto os testes existentes (TS02, TS04) usam 'smartcity-dev-secret'. Sem JWT_SECRET definido no .env, todos os testes que geram tokens manualmente falharão por assinatura inválida.
🟡
BUG-03 — Filtros de query ignorados silenciosamente. Os parâmetros ?categoria=, ?status=, ?regiao= e ?prioridade= são aceitos mas não produzem efeito. A API retorna todos os registros sem filtrar, e nenhum erro ou aviso é retornado ao cliente.
🔵
OBS-01 — Console.log de debug em produção. O método updateDenunciaPrioridade em denunciaService.ts contém múltiplos console.log de debug (incluindo emojis) que devem ser removidos antes de ir para produção.
